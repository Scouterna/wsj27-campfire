# 029. Render the guidebook with VitePress

::: info Status
<p><Badge type="tip" text="Accepted" /> <Badge type="info" text="2026-09-15" /></p>
:::

## Context

The guidebook ([ADR 028](028-keep-a-software-guidebook.md)) is Markdown under `docs/`, and it needs to be browsable: a chapter tree, navigation from any page, and search. Plain Markdown on GitHub gives none of that, so the guidebook needs a static-site generator, and the choice has to sit inside the repository's toolchain rather than bring a second one. The chapters and the decision log have to render as one site.

The guidebook also has to show shapes, not only name them – the flow of a request, how work moves from a need to code. Mermaid is already the format those are drawn in, because the agents' plans carry Mermaid flowcharts and a flow drafted there should move into the guidebook unchanged. The constraint underneath is longevity: anything that has to be regenerated by hand will eventually stop being regenerated. The architecture itself – the system in its context, its containers – wants a notation of its own and is decided separately.

## Decision

We render the guidebook with [VitePress](https://vitepress.dev), draw its flows with [Mermaid](https://mermaid.js.org), and publish it to GitHub Pages.

- **The chapters and the decision log render as one site**, the guidebook at the root and the decisions beside it, with the theme's own local search, so no external service is involved.
- **A diagram is a fenced `mermaid` block inside the Markdown it illustrates**, styled to the contingent's graphic profile, so a diagram and its prose live in one file and change together.
- **The site is published to GitHub Pages from `main`**, at the repository's default project URL, deployed by a workflow rather than from a branch of committed output.
- **The configuration lives in `config/vitepress/`** with the repository's other tooling ([ADR 006](006-lint-and-format-with-a-shared-strict-toolchain.md)).

## Consequences

- VitePress is native to the repository's stack, so it adds no second toolchain to install, pin, or keep current.
- Chapters stay plain Markdown, readable on GitHub. Cross-folder links – a guidebook page to a decision – are authored against the site's routes and resolve only in the rendered site.
- Diagrams are source: diffable, reviewed in a pull request, and edited by whoever edits the surrounding text, which is what keeps them true as the system changes.
- Mermaid renders client-side, so its runtime ships to the browser on any page holding a diagram – acceptable for a documentation site, not for the app. Its dependency chain does not fit the module system cleanly, so the build carries a workaround to revisit whenever Mermaid or Vite moves, and dark mode means every diagram color has to read on both backgrounds.
- The default theme is Vue, so any theme extension is written in Vue rather than the app's React. The guidebook shares nothing with the app's runtime.
- The default project URL puts the repository name in every path. Renaming the repository, or moving to a custom domain later, breaks every published link.
- Nothing generated is checked in, so the published site cannot drift from the source it was built from.

## Alternatives considered

- **Astro Starlight, Docusaurus, or Nextra.** Each is a capable documentation framework, and each is heavier for pure Markdown – Astro's island model, Docusaurus's MDX-by-default and separate search plugin, Nextra's tie to Next.js and its build model.
- **MkDocs with Material.** Excellent, and Python. The repository toolchain is Node and pnpm, and a second toolchain for the docs alone is avoidable friction.
- **Plain Markdown on GitHub, no generator.** It fails the need outright: no site, no chapter tree, no search.
- **Hand-exported SVG or PNG for diagrams.** No dependency and no page weight, and the source lives outside the repository, so the export goes stale the first time nobody regenerates it – for documentation meant to outlive the event, the failure most worth avoiding.
- **A different diagram-as-code format for flows** – D2, PlantUML, Graphviz. D2 in particular draws better. None is the format the plans are already written in, so adopting one means converting those or keeping two formats for the same kind of diagram.
- **A custom domain on GitHub Pages.** It keeps the site at a domain root, so a rename costs nothing. Setup the guidebook does not need yet, and taking it later changes the published URL, which is the reason to weigh it before the site is linked to widely.
- **Netlify, Vercel, or Scouterna's cluster.** Each would serve a static site well. The first two are another account and another set of credentials; the cluster ties the documentation's availability to the app's deployment for no benefit.
