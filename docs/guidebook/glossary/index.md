# Glossary

The words the guidebook, the decisions, and the code share, so everyone reads them the same way. Swedish words stay where the contingent uses them – a leader looking for "avdelning" should find it. Where a term has a page or a decision behind it, the entry links there.

## The jamboree

| Term             | Meaning                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| WSJ27            | The 26th World Scout Jamboree, 30 July – 8 August 2027 on Wyspa Sobieszewska in Gdansk, Poland. The 27 is the year, not the ordinal. |
| Bravely          | The jamboree's theme. Bravely Script, Campfire's display typeface, takes its name from it.                                           |
| WOSM             | The World Organization of the Scout Movement, which owns the World Scout Jamboree.                                                   |
| ZHP              | Związek Harcerstwa Polskiego, the Polish Scouting and Guiding Association, which hosts WSJ27 with WOSM.                              |
| Scouterna        | The Guides and Scouts of Sweden, which sends Sweden's contingent and owns Campfire.                                                  |
| Contingent       | A national delegation to the jamboree. Sweden's is well over two thousand people, the largest it has ever sent.                      |
| Unit (avdelning) | The contingent's basic group of 36 scouts and 4 leaders. The participants service calls it a troop.                                  |
| Patrol           | Nine scouts and an adult patrol leader; four patrols make a unit. The IST are divided into patrols of their own.                     |
| Subcamp          | One of the camps the jamboree site is divided into, grouped in hubs. A unit camps in one.                                            |
| Rundresa         | The round trip – a tour through Latvia and Lithuania before the camp, leaving Sweden 21–22 July 2027.                                |
| Direktresa       | Direct travel, leaving Sweden 26–27 July 2027 by way of Olsztyn, without the tour.                                                   |
| Egen resa        | Own travel – a journey an IST member books and pays for themselves.                                                                  |
| Förträff         | A pre-camp meeting where a unit gets to know each other and prepares together.                                                       |
| Discord          | Where the contingent talks day to day. Campfire deliberately does not integrate with it – see [Scope](../requirements/scope).        |

## The people

| Term                      | Meaning                                                                                                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deltagare                 | A participant – a scout aged 14 to 17. They appear in the list of participants but do not use Campfire.                                                                                                          |
| Ledare                    | A unit leader, the audience Campfire is shaped around first. See [Leaders](../context/people/leaders).                                                                                                           |
| IST                       | International Service Team – adult volunteers, 18 and over, who staff the camp.                                                                                                                                  |
| CMT (kontingentledningen) | The contingent management team, Campfire's other audience: Administration, Communication, Program, Head of Contingent, and Support. See [Context](../context/).                                                  |
| HoC                       | Head of Contingent – the people who lead the contingent and answer for it. See [Head of Contingent](../context/people/cmt-head-of-contingent).                                                                   |
| Support                   | The CMT function in three parts, each an audience of its own – [Health](../context/people/cmt-health), [IST support](../context/people/cmt-ist-support), and [Unit support](../context/people/cmt-unit-support). |
| Audience                  | One of the groups of people the architecture model draws, named the same way in the issue templates, so an issue and a diagram name the same group.                                                              |
| Role                      | What a person is in the contingent – a unit's leader, or a CMT function – as their session carries it.                                                                                                           |
| Health grant              | The right to read health answers outside a leader's own unit, held by the health role or granted per person. See [Participants service](../context/systems/participants-service).                                |

## The product

| Term                     | Meaning                                                                                                                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Campfire                 | The Swedish contingent's digital companion for WSJ27, for the leaders and the contingent management team.                                                                                                                                                                        |
| The web application      | The React application, built with Vite, that holds every screen and installs from the browser ([ADR 014](/decisions/014-build-the-web-application-on-react-with-vite)). See [Applications](../architecture/applications).                                                        |
| Shell                    | A thin native app, on Android or Apple, that hosts the web application in a webview and owns only what the web cannot reach ([ADR 010](/decisions/010-deliver-the-front-end-as-one-web-application-in-native-shells)).                                                           |
| Tier                     | Whether the application runs in a browser or in a shell, read once from the User-Agent before anything renders.                                                                                                                                                                  |
| Bridge                   | The versioned message contract between the web application and a shell – screen, session, and theme out; navigation and actions back ([ADR 018](/decisions/018-bridge-the-web-application-and-the-shells-with-versioned-messages)). See [Bridge](../architecture/layers/bridge). |
| Module                   | A feature module – one domain capability that never imports another ([ADR 016](/decisions/016-compose-the-web-application-from-feature-modules)). See [Modules](../architecture/modules).                                                                                        |
| Library                  | A generic package any module may use. A library that knows a feature is a module in the wrong place.                                                                                                                                                                             |
| Composition root         | The web application itself – the one place that knows every module and assembles them into an application.                                                                                                                                                                       |
| Widget                   | UI a module registers under an id, so another module's screen can show it without importing it.                                                                                                                                                                                  |
| Message                  | A note from the contingent on the start screen, addressed by role and closed per device. Not a bridge message.                                                                                                                                                                   |
| Address                  | A route path marked with the module that owns it, so two modules claiming the same path fails to compile.                                                                                                                                                                        |
| Section                  | A top-level destination in the menu, offered by role. In a shell, the sections are the native tabs, and the web decides what they are.                                                                                                                                           |
| Theme                    | One of the contingent's colors, applied by name, and each unit works in one. The bridge carries the name, never a color. See [Design](../design/).                                                                                                                               |
| The list of participants | The contingent's people with their units, roles, travel, contact details, and health answers. Every answer is scoped by who is asking.                                                                                                                                           |
| Information level        | How much of a person's record comes back. The fullest level adds the health answers, which a unit's own leaders and holders of a health grant may read.                                                                                                                          |
| Environment              | Local, dev, or prod, told apart by what answers behind the back-end paths on the same origin ([ADR 012](/decisions/012-run-campfire-in-three-environments-on-one-origin)). See [Environments](../development/environments).                                                      |
| The one origin           | The single address the application and its back-end answer on – `http://localhost:8000` while developing, `campfire.wsj27.se` in production – so the application fetches only relative paths.                                                                                    |
| ScoutID                  | Scouterna's single sign-on, and how a person signs into Campfire. See [ScoutID](../context/systems/scoutid).                                                                                                                                                                     |
| Scoutnet                 | Scouterna's membership system, where the list of participants comes from. See [Scoutnet](../context/systems/scoutnet).                                                                                                                                                           |
| The auth service         | The WSJ27 back-end service that signs a person in through ScoutID, on Campfire's own origin ([ADR 019](/decisions/019-authenticate-on-the-app-origin-through-scoutid)). See [Auth service](../context/systems/auth-service).                                                     |
| The participants service | The service in the WSJ27 project's back-end that serves the list of participants and decides who may read what. See [Participants service](../context/systems/participants-service).                                                                                             |
| The mock                 | A stand-in for the whole back-end, so local work and tests touch no network ([ADR 021](/decisions/021-develop-against-a-mock-back-end)). See [The mock back-end](../testing/mock).                                                                                               |
| Persona                  | One of the mock's seeded people. Signing in locally is picking one by name, with no password.                                                                                                                                                                                    |

## The code

| Term             | Meaning                                                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Screen           | A whole destination a module answers at an address. See [Presentation layer](../architecture/layers/presentation).                                                                                                 |
| Domain model     | What a module knows a thing to be, independent of how a service shapes it. See [Domain layer](../architecture/layers/domain).                                                                                      |
| The boundary     | Where an untyped answer from a service is checked and becomes a domain model. A bad row in a list is dropped rather than trusted. See [Data layer](../architecture/layers/data).                                   |
| Role translation | The one table that turns the role spellings a session carries into the roles the application knows. An unknown spelling grants nothing ([ADR 019](/decisions/019-authenticate-on-the-app-origin-through-scoutid)). |
| Public surface   | The only part of a package others may import. See [Code organization](../architecture/code-organization).                                                                                                          |

## Documenting the system

| Term               | Meaning                                                                                                                                                                                         |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Software guidebook | This site – a living description of Campfire as designed, rewritten when the design changes ([ADR 028](/decisions/028-keep-a-software-guidebook)).                                              |
| ADR                | Architecture Decision Record – a numbered record of a decision and the alternatives it ruled out. A changed decision gets a new record. See [Decisions](/decisions/).                           |
| C4 model           | The notation of the architecture diagrams, all drawn from one model at system context, container, and deployment level ([ADR 030](/decisions/030-model-the-architecture-as-c4-in-structurizr)). |
| Container          | A C4 level; here always a real package or app – the web application, a shell, a module, a library – never an invented grouping.                                                                 |
| Structurizr        | The tool the model is written for. Its browser UI is the only thing that lays out the diagrams.                                                                                                 |

## Tooling and process

| Term                 | Meaning                                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The checks           | Formatting, lint, Markdown, and types, run separately so one pass reports every failure. See [The checks](../development/checks).                                                                                                                                |
| Vitest               | The TypeScript test runner ([ADR 022](/decisions/022-test-typescript-with-vitest)). See [Unit tests](../testing/unit).                                                                                                                                           |
| The walks            | The Playwright walk-throughs of the web application, each module owning its own ([ADR 024](/decisions/024-walk-through-the-web-application-per-module-with-playwright)). See [UI tests](../testing/ui).                                                          |
| Storybook            | The catalog of every component, widget, and screen ([ADR 023](/decisions/023-catalog-the-ui-in-storybook)).                                                                                                                                                      |
| GitHub Actions       | Where the checks, the builds, and the releases run, as small workflows that each report their own status ([ADR 009](/decisions/009-check-and-release-with-small-github-actions-workflows)). See [Continuous integration](../development/continuous-integration). |
| XcodeGen             | The generator that rebuilds the Apple shell's Xcode project from a spec, so the project is an output rather than a file people merge ([ADR 020](/decisions/020-generate-the-xcode-project-with-xcodegen)).                                                       |
| Caddy                | The web server in front of every environment and inside the deployable image, which makes one origin out of the application and the back-end services.                                                                                                           |
| CalVer               | The version scheme, `YEAR.FEATURE.PATCH`, one version per artifact worked out from its commits ([ADR 034](/decisions/034-version-each-artifact-from-its-own-commits)). See [Release](../maintenance/release).                                                    |
| Release tag          | The git tag that holds an artifact's version, and the source of truth for it – the tree itself holds only `0.0.0`.                                                                                                                                               |
| Promotion            | Pointing prod at a released web image, the same one dev ran. A rollback promotes an earlier version ([ADR 035](/decisions/035-promote-the-web-by-moving-environment-tags)).                                                                                      |
| Conventional Commits | The commit message format, enforced by a hook, whose type decides how far a version moves.                                                                                                                                                                       |
| Agent                | A written role – analyst, architect, developer, or reviewer – that does the work between human decisions. See [Process](../process/).                                                                                                                            |
| Skill                | Domain knowledge an agent, or a person in the Claude apps, reads, published by bumping its version ([ADR 025](/decisions/025-publish-agent-skills-as-versioned-releases)).                                                                                       |
| Spec folder          | The requirements and design for a piece of work while it is built – scratch, never committed. The issue and the code are the record.                                                                                                                             |
