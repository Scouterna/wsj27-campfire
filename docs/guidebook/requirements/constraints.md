# Constraints

These are the fixed boundaries Campfire is built inside. Each one is a decision already made and written down, so this page names the constraint and points at the reasoning rather than re-arguing it. What Campfire is held to once it is inside them is on [Quality attributes](./quality).

| Constraint                   | What it means                                                                                                                                                                                                                                      | Recorded in                                                                                                                                            |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| One web application          | Every screen is built once, in the web application. The Android and the Apple shell are thin by rule and own only what a webview cannot reach.                                                                                                     | [ADR 010](/decisions/010-deliver-the-front-end-as-one-web-application-in-native-shells)                                                                |
| One origin                   | The application and every back-end service under `/api/` answer on the same origin, one prefix per service. The front-end only ever fetches origin-relative paths, so it never learns which environment it is running in.                          | [ADR 012](/decisions/012-run-campfire-in-three-environments-on-one-origin), [ADR 012](/decisions/012-run-campfire-in-three-environments-on-one-origin) |
| A versioned bridge           | What crosses between the web application and a shell is a versioned JSON contract, not an internal call. A shell already on a phone cannot be updated in step with a web deploy.                                                                   | [ADR 018](/decisions/018-bridge-the-web-application-and-the-shells-with-versioned-messages)                                                            |
| Offline-capable during camp  | Reads answer from cache first, and the cache survives a restart. Connectivity on the island is a hope, not an assumption.                                                                                                                          | [ADR 017](/decisions/017-route-and-load-data-with-tanstack-router-and-query)                                                                           |
| Borrowed identity            | Sign-in goes through ScoutID. The session is httpOnly cookies on the application's own origin, and the web application never sees a token.                                                                                                         | [ADR 019](/decisions/019-authenticate-on-the-app-origin-through-scoutid)                                                                               |
| The back-end lives elsewhere | The services are Python, one repository each, outside this one. This repository cannot add an endpoint, only ask for one.                                                                                                                          | [ADR 013](/decisions/013-build-the-back-end-as-python-services-in-their-own-repositories)                                                              |
| One monorepo                 | The web application, both shells, the modules, the libraries, the tooling, and this guidebook are one repository, versioned together.                                                                                                              | [ADR 002](/decisions/002-organize-as-a-single-monorepo)                                                                                                |
| TypeScript, ESM, Node 24     | One language across the front-end and the tooling, ES modules only, the runtime pinned in `.tool-versions`.                                                                                                                                        | [ADR 004](/decisions/004-build-on-pnpm-and-typescript)                                                                                                 |
| TypeScript stays on 6.x      | `typescript-eslint` needs the JavaScript compiler API for its type-aware rules and does not accept TypeScript 7, and strict peer dependencies make that a failed install rather than a warning. Everything moves in one step once it is supported. | `AGENTS.md`                                                                                                                                            |
| Pinned, aged dependencies    | Exact versions, and nothing published less than three days ago will install. Adding a dependency is a deliberate act, and this week's release may simply not be available.                                                                         | [ADR 005](/decisions/005-pin-every-dependency-and-let-new-releases-age)                                                                                |
| Warnings are failures        | Formatting, lint, Markdown, and types all run at zero tolerance, across TypeScript, Kotlin, and Swift. There is nothing to triage later.                                                                                                           | [ADR 006](/decisions/006-lint-and-format-with-a-shared-strict-toolchain)                                                                               |

Three more constraints are less about technology and more about the shape of the work.

- **The team is two people.** Every choice on this page has to be one two people can carry through an eighteen-month build and a camp – which is why there is one web application instead of two native ones, why the tooling is strict enough to settle arguments without a reviewer, and why an approach that needs a platform team loses on sight.
- **The deadline is a date on a calendar.** The jamboree runs 30 July – 8 August 2027, and the contingent's own journey is longer: the round trip leaves Sweden on 21–22 July and the last people are home on 9–10 August. Nothing about those dates moves, and a feature that is not ready for camp is a feature that missed the event it existed for.
- **During camp, the only fix that ships is a web deploy.** For three weeks the people who need Campfire are in a field in Poland and the people who could fix it are on the same field, on their phones. A store review in the middle of that is not a recovery plan. This is the force behind almost everything above, and it is stated in full on [Quality attributes](./quality).

Two costs come with the web-first constraint and are accepted knowingly. An app that is a sign-in screen around a website risks Apple's guideline 4.2 on minimum functionality, which is why the shells carry real native behavior – native chrome, tabs, and the identity flow – rather than wrapping a page and stopping. And how the shells reach a phone at all, whether through the public stores, TestFlight, or managed distribution, is open ([Release](../maintenance/release)).
